## 전체 구조

![CallSign의 서비스와 신뢰 경계, 미연결 경로를 표시한 구조도](assets/architecture.svg)

**범례:** 실선은 해당 요청·검증·직접 통화 코드가 있는 경로이며 실환경 성공을 뜻하지 않습니다. 점선은 목표 구조 또는 제품 연결이 남은 경로입니다. PBX 제어·서명 코드는 추가됐지만 화면·사건 처리·자동 회수·배포 연결이 남아 있습니다. 그림의 `v2`는 현재 직접 통화 코드를, outbox·quota·checkpoint는 각각 후속 작업 보관함·사용 한도·저장한 기준 상태를 뜻합니다.

| 구성 요소 | 책임 | 현재 상태 |
|---|---|---|
| 기관 업무 시스템·Issuer Gateway(기관 승인 서비스) | 모의 고객관리·이상거래 업무 검사, 개별 승인 서명, 승인 사용·취소의 순서 결정 | 직접 통화 API·화면과 교환기 경로 서버 코드. 실제 금융기관 연결 없음 |
| Sender Agent(콜센터 서명 서비스) | 콜센터 장기키 보유, 서버의 서명 요청·할당 업무·브라우저 공개키에 서명 | 직접 통화용 단기 허가와 새 경로의 요청별 서명 코드 |
| Platform API(플랫폼 요청 중계) | 인증된 사용자 요청과 서명 데이터 전달 | 기관·콜센터 개인키와 기관 업무 DB 쓰기 계정 없음 |
| PostgreSQL | 업무·일회 사용 영수증·감사·로그인 세션·후속 작업 저장 | SQL·저장소 코드. 실제 schema 적용·권한·동시성 검증 전 |
| 수신 웹·verifier(검증 모듈) | 서명·권한·세션·실제 연결을 직접 대조 | 직접 통화 화면 연결. 교환기 검증은 화면 호출·변조 시험 보강 필요 |
| Asterisk PBX(교환기)·제어 계층 | 웹 통화 음성 종단, 채널·브리지 연결 사실의 서명 | 채널 조회·음소거·브리지 제어·증거 서명·브라우저 SIP 코드. 전체 경로 미완성 |
| Besu 검증자 4개 | QBFT(허가된 검증자 사이 합의)와 권한 계약 실행 | 구성·계약 코드. 현재 코드 실환경 검증 미실행 |
| Witness(상태 증언자) 4개 중 3개 | 각자의 원장 조회로 같은 블록·상태를 확인하고 서명 | 집계·검증 코드, 메모리 대체 응답으로 단위 시험 |
| STT·규칙·LLM | 상대 음성 전사, 정책 위반 근거 생성·수정·철회 | 직접 통화 화면과 추가 서버 경로 코드. 외부 제공자는 미호출 |

## 통화와 AI 경로

```mermaid
flowchart LR
  subgraph clients[브라우저 경계]
    AG[상담원 웹]
    RE[수신 웹과 검증 SDK]
  end
  AST[Asterisk 통화 채널과 음성 브리지]
  CTRL[CallSign PBX 제어·증거 서명]
  API[기관 서비스의 오디오 수신]
  STT[Deepgram 스트리밍 STT]
  ANA[전사 수정·정책 규칙과 Anthropic LLM]
  AG -. 목표 SIP WSS·암호화 음성 .-> AST
  AST -. 목표 SIP WSS·암호화 음성 .-> RE
  CTRL -->|ARI 채널·Call-ID·브리지 조회 코드| AST
  CTRL -. 화면 연결이 남은 서명 증거 .-> RE
  AG <-->|기존 브라우저 직접 통화 코드| RE
  RE -->|동의한 상대 음성만 전송| API
  API -->|서버 전용 제공자 키| STT
  STT --> ANA
  ANA -->|현재 발화·수정 번호의 위험 이벤트| RE
```

STT는 음성→문자 변환, LLM은 언어 모델입니다. 규칙·LLM은 연락 권한을 발급하거나 통화를 자동 제어하지 않습니다. 분석 서버가 수신자의 실제 상대 음성만 받도록 클라이언트에서 상대방 수신 오디오를 선택합니다. 악성 클라이언트가 오디오 자체를 바꾸는 것까지 서버가 증명하지는 못합니다.

**브라우저의 암호화 음성을 끝내고 다른 채널로 연결하는 미디어 종단(media edge)은 Asterisk입니다.** 별도 Janus나 외부 미구현 Edge API를 필수 종단으로 두지 않습니다. 기존 `MediaEdgeAdapter`는 이전 설계의 호출 도우미로 남아 있으며 새 경로의 구현 근거가 아닙니다. Asterisk ARI(HTTP 제어 인터페이스) 조회 성공은 실제 RTP(음성 패킷) 전달 성공이 아니므로 별도 통화 검증이 필요합니다. [Asterisk 공식 ARI 문서](https://docs.asterisk.org/Configuration/Interfaces/Asterisk-REST-Interface-ARI/)

SIP는 통화 제어, WSS는 암호화 웹소켓, DTLS-SRTP는 브라우저 음성 전송 보안 방식입니다. 브리지는 교환기에서 두 통화 채널을 연결하는 기능입니다.

## 개인키와 데이터의 경계

| 보유 주체 | 비밀·데이터 | 브라우저·온체인 전달 범위 |
|---|---|---|
| 기관 승인 서비스 | 기관 승인 Ed25519 개인키, 업무·고객·승인·소비 DB 접근 | 서명 객체만 전달, 기관 개인키는 전달하지 않음 |
| 콜센터 서명 서비스 | 서비스 Ed25519 개인키 | 세션 공개키에 대한 요청별 서명만 전달 |
| 상담원·수신 웹 | 통화별 단기 개인키, 마이크·상대방 음성 | 공개키·일회성 난수·소유 증명만 전달 |
| PBX 증거 서명 계층 | 별도 증거키, SIP 채널·브리지 매핑 | 세션에 결합한 JWS 증언. 상담원 개인 신원 증명이 아님 |
| Witness·관리 승인자 | 각자 자기 역할의 키 | Witness 상태 서명 또는 관리 명령 서명. 두 키 집합은 별개 |
| PostgreSQL | 고객 식별자·업무·권한·영수증·감사·로그인 세션 | 고객·통화 원문은 원장에 기록하지 않음 |
| Besu 계약 | 기관·위임 내용 해시·키·권한 세대·기간·철회 | 공개 검증에 필요한 권한 상태만 저장 |
| 분석 제공자 | Deepgram: 동의한 상대 음성·모델/언어 설정. Anthropic: 전사·목적 정책(원음 제외) | 원음 기본 미보관은 CallSign 정책이며 제공자 보관 설정까지 보장하지 않음 |

기관 승인 서비스가 원장 관리자·정지키도 읽는 경계는 남은 위험입니다. 서비스 간 인증 비밀값과 웹 코드·신뢰할 공개키 목록(trust bundle)을 배포하는 운영자도 신뢰 대상입니다. 파일 접근을 나눴다는 이유만으로 완전한 격리를 달성한 것은 아닙니다.

## 서버컴과 GCP

현재는 64GB 서버컴에서 **오프라인 개발** 중입니다. 이후 같은 소스·이미지·Compose 구조를 GCP VM으로 옮길 계획이며, VM·도메인·인증서·외부 로그인(OIDC)·통화 중계(TURN)·운영 키·이미지 내용 해시를 별도로 준비해야 합니다. DB·체인 데이터·키·신뢰 설정은 영속 보관하고, 일반 재시작이 초기화·배포·재발급을 수행하지 않아야 합니다.

한 서버에 Besu·Witness를 여러 개 둬도 전원·디스크·호스트 관리자 장애가 공유됩니다. 독립 기관 분산 운영의 증거는 아닙니다. GCP 실제 생성·배포·재시작·복원도 아직 검증하지 않았습니다.
