# 블록체인을 사용하는 이유와 비교 대상

수신자별 승인·현재 연결 검증·공식 업무 접근 분리는 중앙 서버와 DB로도 구현할 수 있다. 원장이 추가하는 가치의 가설은 **서로 독립된 운영자가 권한 변경 순서와 정지·복구 규칙을 공동 집행하고, 한 상태 운영자의 응답에만 의존하지 않는 것**이다. 실제 도입 필요·운영 비용·사용자 효과는 아직 검증하지 않았다.

| 조건 | 중앙 상태 서버 + 기관 서명 | 기관별 서명 문서 | QBFT 원장 + 상태 증언자 |
|---|---|---|---|
| 개별 승인·세션·웹 통화 검증 | 구현 가능 | 구현 가능 | 구현 가능 |
| 권한 없는 타 기관 수정 | 접근 통제 | 기관 서명 검사 | 계약 접근 제어 |
| 상태 응답자 한 곳의 거짓말 | 중앙 운영자 신뢰 필요 | 최신 서명 문서의 출처·전달·완전성 확인 필요 | 등록 증언자 4개 중 3개가 같은 블록·상태에 서명해야 함 |
| 정지·복구 순서 | 중앙에서 공동 승인 규칙 운영 가능 | 문서 버전과 변경 순서 조정 필요 | 계약 권한 세대와 원장의 변경 순서 사용 |
| 가용성의 의존 대상 | 중앙 서비스 구성 | 기관별 문서 전달 경로 | 합의 검증자와 증언자 정족수. 증언자 2개를 잃으면 신규 확인 불가 |
| 운영 부담 | 중앙 서비스·DB | 기관별 키·문서 배포 | 검증자 4개·증언자 4개와 공동 운영 추가. 실제 비용 비교 미측정 |

과거 비교 자료의 `C1`은 중앙 서버, `C2`는 기관별 서명 문서, `B`는 원장 방식이다. 이 표는 구조 비교이며 구현된 비교 실험의 측정 결과가 아니다. 중앙 대안을 의도적으로 약화하지 않으며 기관별 문서의 투명성 로그·포함/일관성 증명도 현재 구현하지 않았다.

현재 수신자는 **상태 증언자(Witness)**를 추가로 신뢰한다. 증언자가 각자 원장을 조회한 사실을 서명하는 방식은 블록 헤더·검증자 확정 서명·저장 상태를 직접 확인하는 체인 자체 증명과 다르다. 같은 서버에서 여러 노드를 실행한 것만으로 실제 기관들의 운영 독립성을 입증하지는 못한다. [신뢰·보안 설계](guide/04-TRUST-AND-SECURITY.md), [전체 개발 명세](MASTER-DEVELOPMENT-SPEC.md)의 한계와 함께 읽는다.
