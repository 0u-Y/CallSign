# CallSign 신청 문구 · TEAM Signal

당시 시연은 위임 철회 뒤 통화를 유지하고 인증 표시만 거뒀다. **현재 설계는 명시적 철회 시 통화를 종료**하며, 상태 확인 불가·AI 장애는 별도로 처리한다. 아래 문구의 정책과 실행 수치는 당시 범위다.

- 프로젝트명: CallSign
- 한 줄 소개: 기관이 승인한 연락인지, 전화를 받는 순간 확인하는 블록체인 기반 기관 발신 인증 서비스.
- 제안 트랙: Web3 기반 사회문제 해결
- 팀명·인원·소속: TEAM Signal · 2명 · 충남대학교 컴퓨터융합학부

## 300자 소개

CallSign은 표시된 기관명 대신 개별 연락 승인, 위탁 발신 권한, 현재 웹 통화 연결을 구분해 확인하는 개념검증입니다. 모의 기관이 테스트 고객의 업무에 한정된 승인서를 발급합니다. 수신 웹은 서로 다른 상태 증언자 3개의 서명과 실제 연결을 확인합니다. 당시 시연은 위임 취소 후 통화는 유지하고 인증 표시만 거뒀습니다. 민감한 서류는 별도 로그인과 소유권 검사가 있는 공식 화면에서만 엽니다.

## 700자 소개

고객에게 필요한 질문은 “이 기관이 나에게 이 목적으로 연락하도록 승인했는가, 그 승인이 지금 연결과 같은가”입니다. CallSign은 기관의 서명 승인서, DB의 일회 사용 영수증, 수신자가 새로 만든 서명 요청, 발신키와 실제 웹 통화 연결을 함께 확인합니다. 권한 상태는 Besu 원장의 계약에 기록합니다. 원장 상태를 조회하는 네 증언자(Witness)가 각자 같은 블록·기관·위임을 확인해 서명하고, 수신 웹은 서로 다른 세 서명이 같은 내용인지 검증합니다. 이는 체인 자체 증명을 직접 검사하는 방식이 아니며 증언자들을 추가로 신뢰합니다. 당시 위임 취소 시에는 확인 표시만 거뒀고, 공식 업무는 별도 로그인과 업무 소유권 검사로 보호했습니다. 실제 기관·통신사 참여나 전국 배포를 주장하지 않습니다.

## 1500자 소개

CallSign은 기관 사칭 전화를 승인·현재 권한·실제 연결·후속 행동의 연결 문제로 봅니다. 일반적인 콜센터 업무 위임은 임의 고객에게 연락해도 된다는 뜻이 아닙니다. 모의 A시청 담당자는 특정 테스트 고객·목적·기간의 개별 연락 승인서를 기관 키로 서명합니다. 위탁센터 발신키는 권한 계약에 기록된 세대와 목적 범위 안에서만 사용합니다.

테스트 고객 Alice는 등록한 통화용 단기키와 새 일회성 난수로 이번 요청을 확인합니다. 두 브라우저는 음성·데이터 채널을 같은 WebRTC 연결에서 협상합니다. 수신 측은 승인서·일회 사용 영수증·세션 결합·발신 서명을 대조하고, 실제 원격 인증서가 협상 문서의 지문과 일치하는지 확인합니다. 같은 데이터 채널에서도 양측이 새로운 난수에 서명해 키 소유를 증명합니다. 당시 브라우저 시험에서는 수락 전 음성 전송량 0바이트와 수락 후 생성 음원의 패킷 증가를 관측했습니다. 실제 사람의 마이크·전화망 검증은 아닙니다.

네 Besu 검증자가 권한 상태를 공유하고 네 증언자는 각자의 노드에서 같은 블록과 상태를 조회해 서명합니다. 집계 API는 이를 전달하며 수신 웹이 등록된 서로 다른 세 서명·증거의 시간 범위·과거 상태로의 되돌림을 검사합니다. 당시 시험에서 증언자 한 개 중단 시 세 서명을 제공하고 두 개 중단 시 확인 요청을 거절했습니다. 이 방식은 증언자 집합을 신뢰하며 블록 확정 서명과 저장 상태 증명을 직접 검증하는 경량 체인 클라이언트가 아닙니다.

당시 시연은 원장 위임 취소 후 3초 주기 조회에서 인증 표시를 철회하되 통화는 유지했습니다. 민감한 서류는 `/official`에서 별도 로그인·업무 소유권 검사 후 열었습니다. 동의한 합성 전사문은 권한 검증과 독립된 패널에서 분석했습니다. 규칙과 선택 Ollama 모델 연결 코드는 있었지만 실제 모델 추론은 실행하지 않았습니다. 이 시점의 목표는 통제 환경에서 정상·사칭·복사·취소·복구를 재현하고 증거를 남기는 것이었습니다.

## 문제·해결·차별화·기술·도입

- 문제: 기관 표시 이름과 일반 위임만으로 개별 연락 승인 및 현재 연결을 판단할 수 없다.
- 해결: 수신자별 승인 → 1회 소비 → WebRTC 전송 결합 → 최신 권한 정족수 → 공식 로그인 경로.
- 차별화: 기존 SIP 발신 신원·통화 이유 표시·위임 표준의 역할을 인정하면서 애플리케이션 수준의 개별 승인, 브라우저 전송 대조, 공동 상태 전환, 공식 업무 분리를 한 흐름으로 검증한다.
- 기술: Solidity/Foundry, Besu QBFT, 상태 증언자 4개 중 3개의 Ed25519 서명, JCS/JWS, Fastify/PostgreSQL, WebSocket/WebRTC, React/Playwright.
- 도입 가설: 공동 권한 상태의 운영 필요와 비용 부담 의사는 미검증이며 기관·통신사와 합의한 격리 시험 환경의 실험이 다음 단계다.
- 팀: 양영우는 아키텍처·계약·API·보안 검증, 이가은은 UX·프론트엔드·API 연동·데모 경험을 담당한다.
