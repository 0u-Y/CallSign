# 8분 발표 원고

당시 시연은 위임 철회 뒤 통화를 유지하고 인증 표시만 거뒀다. **현재 설계는 명시적 철회 시 통화를 종료**하며, 상태 확인 불가·AI 장애는 별도로 처리한다. 아래 문구의 정책과 실행 수치는 당시 범위다.

## 0:00–1:00 사용자 문제

기관 사칭 대응은 “화면에 어떤 이름을 보여줄까”에 머무르기 쉽습니다. 하지만 국민의 실제 판단은 이 기관이 나에게 이 목적으로 연락을 승인했는지, 지금 연결이 그 승인과 같은지, 민감한 행동은 어디서 해야 하는지입니다. 일반 위임만으로 임의 고객 연락을 승인해서도 안 됩니다.

## 1:00–2:00 제품

CallSign는 기관 승인, 발신 권한, 현재 연결, 공식 업무를 네 단계로 분리합니다. 국민은 지갑이나 암호자산을 쓰지 않습니다. 모의 기관 담당자는 한 업무의 연락을 승인하고, 위탁센터 브라우저가 실제 WebRTC 발신 종단이 되며, 수신자는 검증 결과와 공식 재확인 행동을 봅니다.

## 2:00–5:00 라이브 데모

[당시 3분 시연 원고](demo-3min.md)의 정상 → 사칭·복사 → 위임 취소·오래된 상태 → 정지·복구 흐름을 실행합니다. 당시 실제 실행 경로(LIVE)와 고정 시험 데이터를 구분해 소개하고, 연결 확인 화면에서 수락 전 음성 송신 0바이트를 가리킵니다.

## 5:00–6:30 구조와 대안

기관 승인서·수신자의 새 서명 요청·일회 사용 영수증·실제 통화 연결·양측 서명 순서로 설명합니다. 네 원장 노드와 노드별 상태 증언자 네 개가 증거를 제공하며 수신 웹은 같은 내용의 세 서명을 직접 검증합니다. 중앙 상태 서버와 기관별 서명 문서로도 같은 연락 검증을 구현할 수 있음을 인정합니다. 원장의 추가 가치는 여러 운영자가 권한 변경 순서를 공동 집행한다는 가설이며 실제 비용·운영 필요는 미검증입니다.

## 6:30–7:30 도입·검증

Foundry 계약, Vitest 프로토콜·위험 분석, PostgreSQL/API 통합, Playwright와 상태 증언자의 실제 장애 시험을 실행했습니다. 두 브라우저의 연결 인증서와 데이터 채널, 수락 전후 음성 바이트, 원장 철회 후 표시 철회를 측정했습니다. 정확한 건수는 실행별 [당시 시험 결과](../docs/TEST-RESULTS.md)에서 제시하고, 다음 검증은 기관·통신사의 격리 시험 환경에서 운영 필요·비용·사용자 이해를 확인하는 것입니다.

## 7:30–8:00 마무리

CallSign는 “이름을 믿으세요”를 “승인과 현재 연결을 확인하고 공식 경로에서 행동하세요”로 바꿉니다. 상용망 완성을 주장하지 않고, 공동 권한 관리 가설을 정상과 공격 양쪽에서 검증 가능한 형태로 제시합니다.
