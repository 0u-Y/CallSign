# 심사위원 예상 Q&A

## 기존 STIR/SIP Identity/RCD와 무엇이 다른가?

중복되는 문제를 인정합니다. STIR/SIP Identity는 발신 신원, RCD는 이름·통화 이유 표현, RFC 9060은 권한 위임의 중요한 기반입니다. 이 제안의 실험은 애플리케이션 수준의 수신자별 개별 승인, 1회 소비, 브라우저 WebRTC 전송 문맥, 최신 공동 권한 상태, 별도 공식 업무 접근을 하나의 검증 흐름으로 결합하는 데 있습니다. 통신망 표준을 대체한다고 주장하지 않습니다.

## 중앙 DB로도 되지 않나?

됩니다. 승인서·session·WebRTC 검증과 접근 통제는 중앙에서도 구현할 수 있습니다. 원장의 가설은 여러 독립 기관이 상태 변경 순서와 정지·복구를 공동 집행해야 할 때입니다. 실제 수요와 비용 부담이 없다면 중앙 방식이 더 단순합니다.

## witness를 다시 신뢰해야 하는데 탈중앙화인가?

P0은 네이티브 light client가 아니라 별도 3-of-4 상태 증언자 집합을 추가로 신뢰합니다. 한 응답 서버의 거짓말과 stale 반복을 검출하지만 정상 quorum의 공모·공통 오동작은 막지 못합니다. 이 한계를 UI와 문서에 표시합니다.

## 키가 침해되면?

gateway 키만으로 기관 승인서와 소비 영수증을 만들 수 없습니다. issuer만 침해돼도 현재 위임 키·수신 challenge·실제 연결이 필요합니다. issuer와 gateway가 동시에 침해되면 악성 승인 연락이 가능하며, 실제 배포에는 HSM·회전·정지 절차가 필요합니다.

## AI가 틀리면 인증도 바뀌나?

아닙니다. AI/규칙 분석은 읽기 전용 별도 패널이고 계약·verifier·공식 링크를 바꿀 권한이 없습니다. 규칙 fallback과 localhost Ollama adapter를 구현했지만 이번 환경의 실제 LLM 추론은 NOT-RUN이며 정확도 숫자를 제시하지 않습니다.

## 통신사가 도입했나?

아닙니다. 브라우저 1:1 WebRTC로 핵심 결합을 검증했습니다. SIP/RCD/STIR, 착신전환, 회의, TURN, 모바일 OS 표시는 다음 sandbox 범위입니다.

## 개인정보는 블록체인에 무엇을 올리나?

기관과 위임의 key·epoch·목적 mask·기간·정지·취소·directory hash만 올립니다. recipient, 업무, 연락별 row와 SDP는 온체인에 올리지 않습니다. hash도 개인정보가 아닐 거라고 단정하지 않습니다.

## 운영 비용과 가용성은?

중앙보다 validator 4개와 witness 4개가 추가되어 비쌉니다. 실제 시험에서 witness 한 개 중단은 3서명으로 제공됐고 두 개 중단은 503으로 닫혔습니다. 기관별 운영 책임과 비용은 아직 검증하지 않았습니다.
