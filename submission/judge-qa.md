# 심사위원 예상 Q&A

당시 시연은 위임 철회 뒤 통화를 유지하고 인증 표시만 거뒀다. **현재 설계는 명시적 철회 시 통화를 종료**하며, 상태 확인 불가·AI 장애는 별도로 처리한다. 아래 문구의 정책과 실행 수치는 당시 범위다.

## 기존 STIR/SIP Identity/RCD와 무엇이 다른가?

중복되는 문제를 인정합니다. STIR/SIP Identity는 발신 신원, RCD는 이름·통화 이유 표현, RFC 9060은 권한 위임의 중요한 기반입니다. 이 제안의 실험은 애플리케이션 수준의 수신자별 개별 승인, 1회 소비, 브라우저 WebRTC 전송 문맥, 최신 공동 권한 상태, 별도 공식 업무 접근을 하나의 검증 흐름으로 결합하는 데 있습니다. 통신망 표준을 대체한다고 주장하지 않습니다.

## 중앙 DB로도 되지 않나?

됩니다. 승인서·세션·브라우저 통화 검증과 접근 통제는 중앙에서도 구현할 수 있습니다. 원장의 가설은 여러 독립 기관이 상태 변경 순서와 정지·복구를 공동 집행해야 할 때입니다. 실제 수요와 비용 부담이 없다면 중앙 방식이 더 단순합니다.

## 상태 증언자를 다시 신뢰해야 하는데 무엇이 다른가?

이 방식은 체인 자체를 직접 검증하는 경량 클라이언트가 아닙니다. 증언자(Witness) 4개 중 같은 상태를 서명한 3개를 신뢰합니다. 한 응답자의 거짓말·오래된 상태의 반복은 검사하지만 정상 정족수의 공모·공통 오동작은 막지 못합니다. 이 한계를 UI와 문서에 표시합니다.

## 키가 침해되면?

위탁 발신키만으로 기관 승인서와 소비 영수증을 만들 수 없습니다. 기관 승인 시스템만 침해돼도 현재 위임키·수신자 새 서명 요청·실제 연결이 필요합니다. 기관 승인자와 발신자가 함께 침해되면 악성 승인 연락이 가능하며, 실제 배포에는 하드웨어 키 보호(HSM)·교체·정지 절차가 필요합니다.

## AI가 틀리면 인증도 바뀌나?

아닙니다. AI/규칙 분석은 읽기 전용 별도 패널이고 계약·검증 모듈·공식 링크를 바꿀 권한이 없습니다. 규칙 기반 대체 분석과 로컬 Ollama 연결 코드를 구현했지만 이번 환경의 실제 언어 모델 추론은 미실행이며 정확도 숫자를 제시하지 않습니다.

## 통신사가 도입했나?

아닙니다. 브라우저 1:1 WebRTC로 핵심 결합을 검증했습니다. SIP/RCD/STIR, 착신전환, 회의, TURN, 모바일 OS 표시는 별도 격리 환경에서 시험할 범위입니다.

## 개인정보는 블록체인에 무엇을 올리나?

기관·위임의 공개키·권한 세대·목적 범위·기간·정지/철회·공식 경로 목록의 내용 해시만 기록합니다. 고객·업무·개별 연락·통화 협상 문서 원문은 기록하지 않습니다. 해시도 다른 정보와 결합될 수 있어 개인정보와 무관하다고 단정하지 않습니다.

## 운영 비용과 가용성은?

중앙 구성에 비해 원장 검증자 4개·상태 증언자 4개를 추가로 운영해야 합니다. 실제 비용 차이는 측정하지 않았습니다. 당시 시험에서 증언자 한 개 중단은 세 서명으로 제공됐고 두 개 중단은 503으로 닫혔습니다. 기관별 운영 책임과 비용은 아직 검증하지 않았습니다.
